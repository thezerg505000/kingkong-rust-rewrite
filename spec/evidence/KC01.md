# KC01 Punch (main document of the Kong combat phase machine; KC02-KC05, KC09, KC17, KC18 point here)
Recovered from Kong's own AI (`k_*`, Kong struct offsets written `Kong+0xNNN`). `k_ETAT_main@0x89a120` is
**0x89a120..0x8a4100** (40 KB); the shared KB export of it failed (timeout, 5-line stub) and the listed size
18817 is wrong, so it was read from the disassembly (objdump of `KingKong8.exe`); the phase starters, hit
functions and receivers are decompiled normally. Tags: `[C]` read from code, `[L]` inferred, `[G]` guess.

## Behaviour (what the game does)
Kong's melee is a **phase machine** (`Kong+0x1adc`, written by `k_exec_set_combat_phase@0x884a10`, read by
`fn@0x8849b0`). Inputs are *latched* button edges. The attack button (latch slot 3) starts a punch (phase 1,
three animation variants chosen from the stick direction); pressed again when the animation is finished or the
animation's cancel flag is up, it chains a second punch (phase 2) and then the chain ends. The special button
(slot 2, the fury button) after a punch is the **upward repel** (phase 3); the attack button after the repel is
the **downward strike** (phase 5), which restarts the punch chain; the special button during the repel (not
carrying anything) is the **chest pound** (phase 4, fury start, see KF01). The jump/roll button (slot 1) does
the dodge (phase 7/8, KC09); attack right after a dodge is the **counter lunge** (phase 6). Whenever the attack
button is pressed and a "grabbable" proposal exists, the same press goes to the grab state instead (KC06).
A punch also nudges Kong forward (step speed 5.0 / 3.0 / 2.0) and snaps its direction to the nearest enemy in a
45 degree cone within 8 units. Hit windows come from animation data (flag), the blow itself is a sweep.

### Input graph [C] (k_ETAT_main phase handlers 0x89aaba..0x89f2d5, second switch 0x89f2e6..)
"Ready" = `ANIM_IsEnded || (object flag 0x100 && any latch)`; not ready -> `fn@0x8873f0` (`Kong+0x1ae0 = 1`),
the phase continues. When ready, tests run in this order and the first latched button wins:
1. **slot 3 (attack)**: sets `Kong+0x380 = 8`, polls the grab proposal `fn@0x7dd5b0(0xc, msg, !carrying, ..)`;
   if one is returned with message bit 8 -> `AI_GotoState(k_ETAT_grab)` (DAT_00b99fc0). Otherwise:
   phase 1 -> `fn@0x884d40(0)` (phase 2); phase 2 -> `fn@0x885010` (end); phase 3 -> `fn@0x884de0` (phase 5) if not
   carrying, `fn@0x884b00(0)` (phase 1) if carrying; phase 5 -> `fn@0x884b00(0)`; phase 7/8 -> `fn@0x884f60`
   (counter lunge); idle/recovery (phase 9 animation 0x1e..., or idle animations in the second switch) -> `fn@0x884b00(0)`.
2. **slot 2 (special)**: if `Kong+0xc != -1`, `Kong+4 == 0` and the proposal poll succeeds: target life == 0 ->
   `fn@0x884e70` (repel), life != 0 -> `fn@0x886b00` (phase 10); else `fn@0x884e70`. In phase 3 itself: `Kong+4 == 0` ->
   `fn@0x884f00` (chest pound), else wait for the animation end.
3. **slot 4 (cancel)**: `k_TEST_Grab@0x8eaaa0` result (a state to go to) or `fn@0x885010`.
4. **slot 1 (jump/roll)**: `fn@0x8851a0`; if it reports a hotspot (`Kong+0xa18`) -> `AI_GotoState` (DAT_00b99f50, climb).
5. nothing latched: `fn@0x885010`.
Phase 9 (recovery) switches on the current animation minus 0x1e: anims 0x1e, 0xad, 0xae, 0xb1, 0xb2 have their own
branches (0xb1 sends message 0xe after anim frame 0x28); everything else runs the same input tests.
Phase 10: after anim frame 0x3c, once (`Kong+0x444`), `k_exec_hit_landed(2, class 0x20, target, damage 2)`.
Phase 3 for a `Kong+4 != 0` Kong never reaches the chest pound.

### The blow (k_exec_zdf_zdc / k_exec_melee_hit) [C]
Per animation the hand bone and sweep direction (`k_exec_zdf_zdc` cases): 0x17,0x108,0x109 bone 0x28; 0x19 bone 0x14;
0x1b bone 0x28 (rotated -90); 0x1d bone 0x28 (rotated); 0x1f `fn@0x88d440`; 0x28..0x2f hit-stun collision (toward
`Kong+0xc70`); 0x3b,0x3e,0x40,0x5f; 0x8f; 0xc2,0xc4,0xc6 held-object swings. Hit sphere = midpoint of the hand
and victim bone positions, extended by direction * 3.0. A victim is skipped if it is already in `Kong+0xd34[]` (list
cleared by `Kong+0xdac = 0` at each phase start), is Kong, the rider `Kong+0x1ac8`, the previous attacker
`Kong+0x18c4`, or (anim 0xe, roll) a "life message 0x10" object. Damage and class: see KC01 Numbers and `combat::blow`.

## Data
Hit windows (the frames at which object flag 1 is up), the cancel-window flag 0x100 and animation lengths are in the
Kong animation bank, not in the exe. The three punch variants are chosen by the angle of the stick to the vector
`Kong+0x11ac..0x11b4` (Kong's facing `[L]`): `side_dot > 0.5` -> 0x1b (3.0), else `back_dot >= 0` -> 0x19, else 0x17
(0x1b when carrying).

## Rust
`crates/kk_mechanics/src/kong/combat.rs`: `Phase`, `punch_variant`, `phase_params`, `recovery_anim`, `Latched`,
`ComboCtx`, `next_phase` (the input graph), `blow`/`BlowCtx` (damage + class table), `hit_shake_amplitude`. Tests
`combo_graph`, `punch_variants_and_step_speeds`, `blow_table_matches_melee_hit`, `blows_against_the_vrex_rules`.

## Gaps
* Hit-window frames, cancel flag frames and animation durations (animation bank).
* PS2 face-button identity of the four latch slots; the numeric value of the "reference vector" `Kong+0x11ac`.
* `Kong+4` meaning (carrying Ann `[L]`, from `k_reflex` and `k_ETAT_grab_ANN`); K12 owns it.
* The phase-9 per-animation branches for anims 0xae/0xb1/0xb2 were read only superficially.
* Rate 60 Hz for frame counters (`fn@0x425950`) is `[G]`.
